# 작업 시작: $ARGUMENTS

아래 순서를 **반드시 차례대로** 따른다. 단계를 건너뛰지 않는다.

## 1. 이슈 읽기

- 인자가 `T`로 시작하는 ID면: 이 저장소에서 본문에 `todo-id: $ARGUMENTS`가 있는 이슈를 찾는다
  `gh issue list --state all --search "$ARGUMENTS in:body" --json number,title,body,state,labels,milestone`
- 인자가 번호면: `gh issue view <번호> --json number,title,body,state,labels,milestone`
- 이 저장소에서 찾지 못하면 멈추고 알린다 (다른 저장소의 할 일일 수 있음)
- 이슈가 이미 닫혀 있으면 멈추고 알린다

이슈 본문에서 **ID, 주차, 마일스톤, 예상 시간, 브랜치**를 정리해 짧게 보여준다.

## 2. 기획 감시자 판단

`plan-guardian` 서브에이전트에게 이 할 일(ID, 제목, 주차, 마일스톤)을 넘겨 판단을 받는다.

- **진행**: 3단계로
- **주의**: 감시자의 이유를 보여주고, 진행할지 사용자에게 묻는다. 답을 받기 전에는 멈춘다
- **보류**: 이유와 감시자가 제안한 대안(먼저 할 일, 계획 변경안)을 보여주고 **멈춘다**

계획을 바꿔야 한다는 결론이면 코드를 쓰지 않는다. 계획 변경은 기획 저장소(`../wizard-app-planning`)에서 한다:
문서 수정 → `docs/17-weekly-todo.md` 표 수정(ID 유지) → `pnpm issues:sync`.

## 3. 관련 기획 문서 읽기

`CLAUDE.md`의 문서 표를 기준으로 이 할 일에 필요한 문서만 읽는다. 최소한:

- **15-dev-plan.md**: 이 마일스톤의 완료 기준
- **16-architecture.md**: 해당 부분 + 16장 형식 약속
- 할 일에 따라: DB → 10, 박사 → 12·13, 화면 → 08·09, 기록 규칙 → 04, 지식 → 14

## 4. 계획 제시 — 여기서 멈추고 승인을 기다린다

아래 형식으로 보여준다. **승인 전에는 파일을 만들거나 고치지 않는다.**

```
### 무엇을
(이 할 일이 끝나면 할 수 있게 되는 것, 한두 문장)

### 먼저 쓸 테스트
- (15 완료 기준, 10 예외 상황, 13 정답지에서 가져온 기대 동작)

### 바꿀 파일
- 경로 — 무엇을, 왜

### 영향
- 형식 약속(16장) 변경: 있음 / 없음
- 마이그레이션: 있음 / 없음
- 다른 저장소 작업 필요: 있음 / 없음 (있으면 같은 브랜치 이름, backend 먼저)
- 미정 사항 결정 필요: 있음 / 없음 (있으면 후보와 장단점, 결정은 사용자가)

### 커밋 계획
- 이모지 커밋 규칙으로 2~5개의 작은 커밋
```

## 5. 승인 후

1. 브랜치: `dev` 최신을 받아 이슈의 브랜치 이름으로 생성 (이미 있으면 전환)
   `git switch dev && git pull && git switch -c <브랜치>`
2. **테스트부터** 작성하고, 실패하는 것을 확인한 뒤 구현
3. 계획에 없던 파일을 바꿔야 하면 멈추고 이유를 설명한 뒤 승인을 받는다
4. 작은 단위로 커밋 (`CLAUDE.md` 커밋 규칙)
